[bug · medium] `createFolder` and `deleteFolder` perform a read-modify-write on the metadata
(loadFolders → mutate → saveFolders) without any synchronization or lock. If two folder operations
are triggered concurrently (e.g., rapid successive deletes/creates, or a create racing a delete),
one save can clobber the other's change, silently dropping a folder's metadata. Since this commit is
specifically hardening metadata/disk consistency, consider serializing these mutations (e.g., a
static `Future`-chained mutex in StorageService) so the load-modify-save window is atomic. The same
applies to FolderProvider.renameFolder/recolorFolder which call saveFolders directly.

[maintainability · low] `_replaceFolder` reconstructs `FolderData` field-by-field. `FolderData`
currently has 4 fields so nothing is dropped today, but this manual copy is fragile: if a field is
later added to `FolderData`, this reconstruction will silently reset it to the default and cause

─── lib/services/storage_service.dart:320-328 ───
[bug · low] The new ordering (save metadata first, then delete the physical dir) widens a TOCTOU
window: the emptiness check at line 314 happens before the metadata write, and only afterwards is
`folderDir.delete()` attempted. If a video is moved into this folder via `moveVideo` during that
window, the metadata entry has already been removed (folder tag disappears) while the physical
delete fails silently, leaving an orphaned video in a folder that no longer appears in the UI.
Consider re-checking emptiness immediately before the delete (or treating a failed non-empty delete
as a reason to restore the metadata entry). Given the single-app context this is low risk, but worth
a guard.
